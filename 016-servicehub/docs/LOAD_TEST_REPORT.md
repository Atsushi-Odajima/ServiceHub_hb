## 読み方・注意

- 1組織あたりの規模は 顧客5,000・予約2万・スタッフ50・拠点5(負荷試験目標を100組織に分けた値)。1組織に200万件が集中する使い方は想定・測定していない。
- アプリとDBが同じマシン(4コア)で CPU を分け合っている。本番のホスティング(アプリとDBが別・ネットワーク越し)では1往復ごとに数ms以上が加わる一方、CPU・メモリの多いプランでは速くなる。
- req/s は同じURLを10並行で繰り返したときの上限の目安で、実際の利用(1組織で同時に数人〜数十人)より高い負荷。10並行時の応答時間には Node.js 1プロセスの CPU 待ちが含まれる。
- 空き枠: 1回あたり DB 読み込み約17ms + 計算約7ms(単独実行時)。この測定で見つけた計算の無駄(おまかせ割当の並べ替えで毎回タイムゾーン変換・全件走査)を除き、同じ条件の p50 は scale 0.02 で 311ms → 57ms、全量で 223ms → 約170〜190ms に短縮した(判定内容は同じ。単体・統合テストで確認)。
- 運営KPI は30日分の稼働率(勤務・休憩・予約の区間計算)を含むため重い。期間を指定して表示する画面で、連続した再読み込みは想定しない。
- 予約作成は、枠の排他(advisory lock)・予約エンジンの再判定・占有の確保・履歴/通知/監査の記録を1トランザクションで行うため、読み取りより遅い。
- 再測定: `pnpm load:generate -- --scale 1`(約16分・DB 約8GB)→ `pnpm build && pnpm load:run -- --out docs/LOAD_TEST_REPORT.md`。終わったら `DROP DATABASE servicehub_load` で容量を戻す。

# 運用手順 (OPERATIONS.md)

ServiceHub を運用する人(購入者の管理担当・導入を手伝う人)向けの手順書。
画面での操作は購入者向け説明書(`manual/バックアップと復元.txt` など)にも書いてある。ここではサーバー側の作業を含めて説明する。

---

## 1. 構成とデプロイ

- 構成: Web サーバー(Node.js 22、1プロセス)+ PostgreSQL 16。通知の送信と日次処理(回数券の失効・利用プランの期間締め・待機の期限など)は既定で Web と同じプロセスで動く(`RUN_WORKER=true`)。
- 別プロセスにする場合: Web は `RUN_WORKER=false`、ワーカーは `node dist/server/worker.js`(`pnpm start:worker`)。
- DB の接続ロールは **superuser / BYPASSRLS を持たない**こと(組織間のデータ分離を DB でも強制するため。起動時に検査し、本番では拒否)。
- 必要なもの: Node.js 22 が動く環境(または Docker)と PostgreSQL 16。**購入者のパソコンに開発環境は不要**(ホスティングの画面操作だけで始められる)。
- 公開は必ず HTTPS で行う(Render は自動。Docker の場合はリバースプロキシ等で HTTPS を終端し `TRUST_PROXY=true`)。

### 1.0 最初の組織とオーナーの作り方(3通り)
1. **環境変数(シェル不要・推奨)**: 初回起動時に `SETUP_ORG_SLUG` / `SETUP_ORG_NAME` / `SETUP_OWNER_EMAIL` / `SETUP_OWNER_PASSWORD`(10文字以上)[/ `SETUP_OWNER_NAME` / `SETUP_LOCATION_NAME` / `SETUP_TIMEZONE`] を設定しておくと、本番の組織が1つもない場合だけ組織・最初の拠点・オーナーを作る。ログインを確認したら **`SETUP_OWNER_PASSWORD` を環境変数から削除**する(2回目以降の起動では何もしないが、パスワードを残さないため)。パスワードはログに出さない。
2. **コマンド**: `node dist/server/cli/setup-org.js --slug <URL名> --name <組織名> --owner-email <メール> [--password <10文字以上>] [--location-name 本店]`(パスワードを省略すると生成して1回だけ表示)。
3. **バックアップから**: 別の環境のバックアップファイルから復元する(6.3)。
- 試用のサンプル組織(Sample Wellness)は `SEED_SAMPLE_ON_START=true` で作られる(メールは送信されない。本番の組織とは分離)。
  - **サンプルのログイン情報は説明書で公開されている**ため、実際の顧客が使う環境では作らない(試用用の環境でだけ true にする)。
  - 作った場合は、本番で使い始める前に `SEED_SAMPLE_ON_START` を false にしてから `node dist/server/cli/seed-sample.js --delete` を実行する(サンプル組織とサンプル専用のログインを削除。本番の組織には触れない)。

### 1.1 Render(Blueprint)
リポジトリの `render.yaml` に Web サービス(Docker)と PostgreSQL の定義がある。
1. Render にログインし、「New」→「Blueprint」でこのリポジトリを選ぶ。
2. 入力を求められる値を設定する:
   - `APP_BASE_URL`: 公開URL。**空欄でよい**(Render の公開URL `https://servicehub-xxxx.onrender.com` を自動で使う)。独自ドメインにしたらそのURLを設定する
   - `SETUP_ORG_SLUG` / `SETUP_ORG_NAME` / `SETUP_OWNER_EMAIL` / `SETUP_OWNER_PASSWORD` / `SETUP_LOCATION_NAME`: 1.0 の 1
   - `EMAIL_FROM` / `SMTP_URL`: メールを実際に送る場合(送らない間は空で可。`EMAIL_PROVIDER` を `smtp` に変える)
   - `BACKUP_ENCRYPTION_KEY`: 任意(3.4)
   - `SESSION_SECRET` は自動生成される。**値を控えて安全な場所に保管**する(引っ越し時に同じ値を使う)
3. プラン・リージョン(既定: Web `starter` / DB `basic-256mb` / `singapore`)は料金を公式ページで確認して選ぶ(OPERATING_COSTS.md)。
4. 作成後、デプロイが終わったら `APP_BASE_URL` を開いてオーナーでログインする。確認できたら Render の Environment 画面で `SETUP_OWNER_PASSWORD` を削除して保存(再デプロイされる)。
5. 独自ドメイン: Render の Custom Domains で設定し、`APP_BASE_URL` をそのURLに変更する。
- DB 構造は起動時に自動で更新される(`MIGRATE_ON_START=true`)。複数インスタンスでも同時に適用しないよう排他している。
- Render の PostgreSQL の既定ユーザーは superuser ではないため、RLS による分離がそのまま有効(起動時に検査)。
- DB のバックアップはプランの自動バックアップに加え、組織バックアップ(3章)を併用する。

### 1.2 Docker Compose(自社サーバー・VPS)
1. サーバーに Docker と Docker Compose を用意し、このリポジトリ(またはリリースの圧縮ファイル)を置く。
2. `deploy/docker.env.example` を `.env` にコピーし、パスワード類・`SESSION_SECRET`・`APP_BASE_URL`・`SETUP_*` を設定する。
3. `docker compose up -d --build` を実行する。PostgreSQL の初回起動時に、アプリ用の一般ロール(superuser でない)とデータベースが作られる(`deploy/postgres/init-app-db.sh`)。
4. `APP_BASE_URL` を開いてログインし、`.env` から `SETUP_OWNER_PASSWORD` を消して `docker compose up -d`。
5. HTTPS: 前段にリバースプロキシ(例: Caddy / nginx)を置いて HTTPS を終端し、`TRUST_PROXY=true` にする。
- 更新: 新しい版を置いて `docker compose up -d --build`(DB 構造は起動時に更新)。
- DB のバックアップ: 組織バックアップ(3章)に加え、`docker compose exec db pg_dump -U postgres servicehub > backup.sql` などで DB 全体も保存する。
- イメージ単体: `docker build -t servicehub .` → 環境変数を渡して `docker run -p 3000:3000 ... servicehub`。

### 1.3 その他の Node.js ホスティング
`pnpm install --frozen-lockfile && pnpm build` でビルドし、`node dist/server/index.js` で起動する(本番に必要な依存パッケージは `dependencies` の8つのみ)。環境変数は 1.4 のとおり。

### 1.4 環境変数

| 変数 | 必須 | 説明 |
|---|---|---|
| `DATABASE_URL` | ○ | PostgreSQL の接続文字列 |
| `DATABASE_SSL` | | `disable` / `require` / `no-verify`(ホスティングの指示に従う) |
| `SESSION_SECRET` | ○ | 32文字以上のランダム文字列。**予約管理リンクの生成にも使う。環境を移すときは同じ値を使う**(9.3 参照) |
| `APP_BASE_URL` | ○ | 公開URL(例 `https://reserve.example.com`)。メールのリンクと送信元チェック(CSRF)に使う。Render では省略時に `RENDER_EXTERNAL_URL` を使う。本番で分からなければ起動しない |
| `NODE_ENV` | ○ | 本番は `production` |
| `EMAIL_PROVIDER` / `SMTP_URL` / `EMAIL_FROM` | | 既定 `log`(送信しない)。実送信は `smtp` と SMTP_URL |
| `BACKUP_ENCRYPTION_KEY` | | 設定するとバックアップファイルを AES-256-GCM で暗号化(16文字以上)。**キーを失うと復元できない** |
| `BACKUP_UPLOAD_MAX_MB` | | 画面から復元できるファイルの上限(既定 200MB)。大きい場合はコマンドで復元 |
| `MIGRATE_ON_START` | | `true` で起動時に DB 構造を更新 |
| `RUN_WORKER` | | `true` で Web プロセス内で通知ワーカー/日次処理を動かす |
| `TRUST_PROXY` | | ホスティングのロードバランサ配下では `true`(IP 単位の回数制限を正しく行うため) |
| `TURNSTILE_SITE_KEY` / `TURNSTILE_SECRET_KEY` | | 公開予約の bot 対策(任意) |
| `LOG_LEVEL` | | 既定 `info`。ログには個人情報(メール・電話・氏名・検索語・トークン)を出さない |
| `SETUP_ORG_SLUG` ほか `SETUP_*` | | 初回セットアップ(1.0)。組織が1つもないときだけ使われる。**作成後は `SETUP_OWNER_PASSWORD` を削除** |
| `SEED_SAMPLE_ON_START` | | `true` でサンプル組織を作る(無ければ)。**試用環境だけ**で使う(1.0) |

秘密情報(`DATABASE_URL`, `SESSION_SECRET`, `SMTP_URL`, `BACKUP_ENCRYPTION_KEY`, `TURNSTILE_SECRET_KEY`)はホスティングの環境変数/Secret 機能に保存し、リポジトリやチャットに貼らない。
空欄(空文字)の変数は未設定として扱う(既定値が使われる)。

### 1.5 コマンド一覧(本番=ビルド済み / 開発=pnpm)

| 作業 | 本番(Render の Shell / Docker の exec) | 開発 |
|---|---|---|
| DB構造の作成・更新 | `node dist/server/cli/migrate.js` | `pnpm db:migrate` |
| 本番組織と最初のオーナーを作る | `node dist/server/cli/setup-org.js --slug <URL名> --name <名称> --owner-email <メール>` | `pnpm setup:org -- ...` |
| サンプル組織(作成 / 作り直し / 削除) | `node dist/server/cli/seed-sample.js [--reset \| --delete]` | `pnpm db:seed:sample -- --reset` |
| バックアップ作成 | `node dist/server/cli/backup.js create --org <URL名>` | `pnpm backup:create -- --org <URL名>` |
| バックアップ検証 | `node dist/server/cli/backup.js verify --file <ファイル>` | `pnpm backup:verify -- --file ...` |
| 復元 | `node dist/server/cli/backup.js restore --file <ファイル> [...]` | `pnpm backup:restore -- ...` |

## 2. アップデート手順

1. 画面(設定 > バックアップ)またはコマンドで**全組織のバックアップ**を作成して保管する。ホスティングの DB スナップショットも取れるなら取る。
2. 新しい版をデプロイする(`MIGRATE_ON_START=true` なら起動時に DB 構造が更新される。false の場合は `migrate.js` を実行)。
3. 起動後に `/healthz` が `{"ok":true}` を返すこと、ログインと予約一覧・受付ボードの表示を確認する。
4. 問題があれば、前の版に戻す。DB 構造の更新は追加のみで後方互換を保つ方針だが、戻せない場合は手順 1 のバックアップから復元する(6章)。

## 3. バックアップ

### 3.1 2種類のバックアップ(併用を推奨)

| 種類 | 対象 | 用途 |
|---|---|---|
| ホスティングの DB バックアップ(自動・時点復旧) | DB 全体(全組織) | サーバー障害・DB 破損からの復旧。ホスティングのプランにより保持期間が異なる(OPERATING_COSTS.md) |
| 組織バックアップファイル(`.shbak`) | 1つの組織のすべてのデータ | 誤操作からの復旧、別の環境・別のホスティングへの引っ越し、手元での保管 |

組織バックアップの対象: 組織・拠点(営業時間/臨時休業/受付停止)・スタッフ・メンバーと権限・サービス(事前質問/必要リソース/開催時刻)・リソース・シフト・顧客(メモ・統合履歴)・予約(履歴・事前質問の回答)・待機・実施記録・回数券と台帳・利用プランと台帳・通知履歴・CSV取込履歴・監査ログ。
含まれないもの: ログイン中のセッション、未使用の招待リンク、パスワード再設定リンク、アクセス回数制限の一時データ、定期処理の実行記録。

### 3.2 画面から作成する(Owner のみ)

設定 > バックアップ > 「バックアップを作成してダウンロード」。
- ファイル名: `servicehub-backup_<組織のURL名>_<日時>.shbak`
- 作成の記録は監査ログ(「バックアップ作成」)に残る。画面の「最近のバックアップと復元」にも表示される。
- **ファイルには顧客の個人情報とログイン情報(元に戻せない形のパスワード)が含まれる。** メール・チャットで送らず、アクセスを制限した場所(組織の管理用ストレージ、暗号化した外付けドライブ等)に保管する。
- 目安: 週1回以上、および大きな設定変更・CSV 取込・アップデートの前。最低でも直近3世代を残す。

### 3.3 コマンドで作成する(定期実行)

```
node dist/server/cli/backup.js create --org <URL名> --out /backup/servicehub-<URL名>-$(date +%Y%m%d).shbak
```
- 作成途中のファイルは `.partial` の名前で書き、完了後に名前を変える(途中のファイルをバックアップと取り違えない)。
- `BACKUP_ENCRYPTION_KEY` が設定されていれば暗号化される(`--no-encrypt` で暗号化しない)。
- ホスティングの定期実行(cron)機能で実行し、出力先をオブジェクトストレージ等に保存する(サーバーのディスクは再起動で消える場合がある)。

### 3.4 暗号化キーの管理

- `BACKUP_ENCRYPTION_KEY` を設定すると、以後のバックアップは暗号化される(ファイル先頭が `SHBKENC1`)。
- 復元には**作成時と同じキー**が必要。キーはバックアップファイルとは**別の場所**に保管する(パスワード管理ツール等)。
- キーを変更した場合、古いバックアップの復元には古いキーが必要になる。変更履歴を残す。

## 4. バックアップファイルの形式(技術情報)

- 平文: gzip 圧縮した NDJSON。1行目がヘッダー(形式名・形式の版・DB 構造の版 `schemaVersion`・アプリの版 `appVersion`・作成日時・組織)、表ごとに「開始行 → 行データ → 件数と SHA-256」、最後にフッター(表ごとの件数と全体の SHA-256)。
- 暗号化: `SHBKENC1` + salt + iv + AES-256-GCM(gzip(NDJSON)) + 認証タグ。鍵は scrypt で導出。
- 値は PostgreSQL のテキスト表現(時刻は UTC・マイクロ秒まで)で保存し、復元後に同じ形式で読み直して内容のハッシュを照合する。

---

## 5. 復元の前に: 検証

画面: 設定 > バックアップ > ファイルを選んで「ファイルを確認」(データは変わらない)。
コマンド: `node dist/server/cli/backup.js verify --file <ファイル>`

確認される内容:
- ServiceHub の組織バックアップであること、壊れていない・改ざんされていないこと(表ごとの件数とハッシュ、全体のハッシュ)
- すべての行がヘッダーの組織のものであること(他の組織のデータを混ぜたファイルは拒否)
- DB 構造の版の互換性(新しい版で作ったファイルは、アプリを更新してから復元する)
- 暗号化の有無(暗号化されていて鍵がない/違う場合はここで分かる)
- `SESSION_SECRET` が作成元と違う場合は注意を表示(9.3)

---

## 6. 復元

復元はすべて **1つのトランザクション**で行う。途中で失敗した場合は何も変わらない(現行データはそのまま)。
復元後の照合: 表ごとの件数と内容(ハッシュ)、回数券・利用プランの残数(台帳を元の順に再生し、DB のトリガーで再計算した結果がバックアップと一致すること)。1つでも一致しなければ復元を取り消す。

### 6.1 画面から: この組織をバックアップ時点に戻す(Owner のみ)

1. 設定 > バックアップ > 「バックアップを作成してダウンロード」で**現在のデータ**を保存する(2時間以内のバックアップがないと復元できない。誤ったファイルを選んだ場合に戻すため)。
2. 復元したいファイルを選んで「ファイルを確認」。組織名・作成日時・件数を確認する。
3. 「復元テストを実行」(任意・推奨): 実際に復元と照合を行って最後に取り消す。データは変わらない(数秒間、他の操作が待たされることがある)。
4. 「復元の手続きへ進む」→ 注意事項を読み、「現在のデータのバックアップを保存しました」にチェック、組織の URL 名を入力して「復元する」。
5. 完了すると**全員がログアウト**される。ログインし直して、予約・顧客・回数券の残数などを確認する。

注意:
- バックアップ作成後に登録・変更した予約・顧客・実施記録・回数券の消化などは失われる(復元前に保存したファイルには残っている)。
- バックアップ時点で**未送信だった通知は送信しない**(古い内容のメールを送らないため)。必要なら通知履歴から個別に対応する。
- 未使用の招待リンクは無効になる(招待し直す)。
- 操作者がバックアップ内で有効なオーナーでない場合は、画面からは復元できない(復元後にログインできなくなるため)。コマンドで復元する。
- バックアップに、この組織のメンバーでなかった既存のログインユーザーが含まれていた場合、その人の権限は「無効」で復元される(設定 > メンバーと権限 で確認)。
- 画面から復元できるファイルは `BACKUP_UPLOAD_MAX_MB`(既定 200MB)まで。

### 6.2 コマンドで: 同じ組織を置き換える

```
node dist/server/cli/backup.js restore --file <ファイル> --replace <URL名>            # 確認のため URL 名の入力を求める
node dist/server/cli/backup.js restore --file <ファイル> --replace <URL名> --dry-run  # 復元テスト(最後に取り消す)
```
`--yes` で確認を省略できる(自動化用。誤操作に注意)。

### 6.3 新しい環境(空の DB)へ復元する(引っ越し・災害復旧)

1. 新しい環境の DB を作り、環境変数を設定する。**`SESSION_SECRET` と `BACKUP_ENCRYPTION_KEY` は元の環境と同じ値**にする。
2. DB 構造を作って復元する:
   ```
   node dist/server/cli/backup.js restore --file <ファイル> --migrate
   ```
   (`--database-url <URL>` で復元先 DB を明示できる)
3. アプリを起動し、元の環境と同じメールアドレス・パスワードでログインする(ログインユーザーも復元される。既に同じメールのユーザーがいる場合は上書きせずに紐付け、そのユーザーの既存のパスワードでログインする)。
4. 予約・顧客・回数券の残数・監査ログを確認する。問題なければ DNS 等を新しい環境へ切り替える。

画面だけで引っ越す場合: 新しい環境で `setup-org.js` で仮の組織と**元の環境と同じメールアドレスのオーナー**を作り、そのオーナーでログインして 6.1 の手順(仮の組織のバックアップを作成 → 元の環境のファイルを確認 → 復元)を行う。「別の組織のバックアップ」として確認の項目が1つ増える。復元後は仮の組織は置き換わり、元の組織の URL 名・データになる。

### 6.4 復元テスト(定期的な訓練)

- 3か月に1回程度、最新のバックアップで復元テストを行う(画面の「復元テストを実行」または `--dry-run`)。
- 年に1回程度、空のテスト環境へ実際に復元し(6.3)、ログインして主要画面を確認する。開発・検証環境では `tests/e2e/e2e-7-backup-restore.spec.ts` が同じ手順を自動で行う。

### 6.5 復元できないとき

| 表示 | 原因と対処 |
|---|---|
| 暗号化されたバックアップです / 復号できません | `BACKUP_ENCRYPTION_KEY` が未設定・違う。作成時のキーを設定する |
| ハッシュが一致しません / 破損しています / 途中で切れています | ファイルが壊れている。別の世代のバックアップを使う |
| 新しい版のアプリで作成されたバックアップです | アプリを更新してから復元する |
| この組織は復元先に既に存在します | 新しい環境への復元で、同じ組織が既にある。置き換えるなら `--replace` |
| 組織のURL名は…別の組織が使用しています | 復元先で同じ URL 名を別の組織が使っている |
| 現在のデータのバックアップを作成してください | 6.1 の手順 1 を先に行う |
| あなたの有効なオーナー権限が含まれていない | 画面からは復元できない。コマンドで復元する |
| 台帳…一致しません | ファイルの内容が不整合(改ざん・破損)。別の世代を使う |

いずれの場合も現行データは変わっていない。

## 7. 障害対応

### 7.1 まず確認すること
- `/healthz` の応答(`db: false` なら DB に接続できていない)。
- ホスティングのログ(ログにはメール・電話・氏名・検索語・パスワード・トークンは出さない設計。エラー時も DB の値は出さない)。
- ホスティングの障害情報ページ。

### 7.2 よくある事象

| 事象 | 対処 |
|---|---|
| 画面が開かない / 500 エラー | ログのエラーを確認。DB の接続数上限・ディスク容量を確認。再起動で直る場合はワーカーの暴走がないか確認 |
| 通知メールが届かない | 通知履歴で状態を確認(「失敗」は再送できる)。`EMAIL_PROVIDER=log` のままでないか、SMTP の認証情報・送信元ドメインの SPF/DKIM を確認 |
| 定期処理(回数券の失効など)が動かない | `RUN_WORKER` の設定、ワーカープロセスの起動を確認。処理は冪等なので再開すれば追いつく |
| 予約を誤ってキャンセルした | 予約詳細の「キャンセルを取り消す(復元)」(枠が空いている場合) |
| 回数券・利用プランを誤って消化した | 予約の詳細から「消化の取消」(1回戻す)。数の誤りは回数券/利用プランの詳細で手動調整。いずれも台帳に履歴が残る |
| 大量の誤操作・誤った CSV 取込 | 直前のバックアップから復元(6.1)。復元前に現在のデータも保存する |
| 画面が遅い | LOAD_TEST_REPORT.md の測定条件と比較。DB のプラン(メモリ・CPU)を確認。`ANALYZE` の実行 |

### 7.3 セキュリティ上の事象
- アカウントの乗っ取りが疑われる: 設定 > メンバーと権限 で該当メンバーを「無効」にする(その人のすべてのセッションが即時に切れる)。本人にパスワード再設定を依頼する。監査ログで操作を確認する。
- `SESSION_SECRET` の漏えい: 値を変更して再起動する(全員が再ログインになる。既に送ったメールの予約管理リンクは引き続き使えるが、以後のメールのリンクは新しい値で作られる)。
- バックアップファイルの紛失: 個人情報の漏えいとして組織の手順に従う。暗号化していた場合でもキーの管理状況を確認する。

## 9. 補足

### 9.1 性能の目安
LOAD_TEST_REPORT.md に、負荷試験目標の規模(組織100・予約200万件等)の生成データでの測定結果がある。**販売保証値ではない。**

### 9.2 組織の削除
組織の削除は画面にはない(誤操作防止)。必要な場合は、バックアップを保管したうえで開発者が行う。

### 9.3 SESSION_SECRET と予約管理リンク
予約管理リンク(顧客がメールから予約を確認・変更・キャンセルするリンク)は `SESSION_SECRET` と予約ごとの値から作られ、DB にはハッシュだけを保存している。
環境を移すときに値を変えると、**以後に送るメール**(リマインダー等)のリンクが無効になる。既に送ったメールのリンクは使える。バックアップの検証・復元時に、値が違えば注意を表示する。

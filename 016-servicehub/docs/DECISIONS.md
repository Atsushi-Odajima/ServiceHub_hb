# 設計判断記録 (DECISIONS.md)

各項目: 判断 / 理由 / 代替案。日付は判断時点(2026-09-30 開始)。

## D-001 PostgreSQL を唯一のサーバーDBとする
- 判断: PostgreSQL 16(マネージド Postgres でも動く範囲の機能のみ使用)。拡張は `btree_gist` のみ(PG13以降 trusted extension で非superuserが作成可)。
- 理由: 予約競合を DB 制約で防ぐ `EXCLUDE USING gist`、RLS、advisory lock、`FOR UPDATE SKIP LOCKED` によるジョブ取得が一つのDBで揃う。
- 代替: SQLite(同時書き込み・RLSなし)、MySQL(排他制約なし)→不採用。

## D-002 マルチテナント = 共有スキーマ + organization_id + RLS(FORCE) + 複合FK
- 理由: 小規模組織が多数という前提で運用コストが最小。RLSにより、アプリのバグで WHERE を書き忘れても他組織の行は返らない。
- 注意: superuser / BYPASSRLS ロールでは RLS が効かない → 起動時検査(`checkRlsEffective`)。本番で検査NGなら起動拒否(`ALLOW_RLS_BYPASS_ROLE=true` で明示的に許可した場合のみ警告で継続)。
- 注意: RLS 下では leakproof でない演算子(`LIKE`, `&&`, `@>`)が索引条件に使えない(Phase0 PoCで確認)。範囲重複は比較演算、検索は正規化列の前方一致で書く。
- システム文脈(`app.system=on`)はログイン照合、公開ページの組織解決、予約管理トークン照合、ジョブ、移行、バックアップに限定。

## D-003 ORM を使わず手書き SQL
- 理由: 予約確定はロック順序・排他制約・RLS設定を厳密に制御する必要がある。全クエリは `$1` プレースホルダのパラメータ化のみ(文字列連結でSQLを作らない)。識別子を動的にする箇所(ソート列など)はホワイトリストで選択。

## D-004 予約競合防止は三層
1. 候補表示時: 予約エンジン(純関数)で空きを計算。
2. 確定時: 同じエンジンをトランザクション内で再実行。事前に対象スタッフ/リソース/拠点(同時受付上限設定時)の advisory lock を固定順で取得。
3. 最終防衛線: `occupancies` の排他制約(同一スタッフの有効占有は拠点をまたいでも時間重複不可)、定員 `CHECK (seats_taken <= capacity)`、冪等キー UNIQUE。
- PoC: 同一枠へ30並行 → 成功1件(ロックあり/なしとも)。

## D-005 「占有(occupancy)」と「予約(booking)」を分離
- 1:1 サービスは予約1件 = 占有1件。定員制サービスは同一(拠点, サービス, スタッフ, 開始時刻)の占有に複数予約が相乗り(seats_taken)。
- スタッフ/リソースの時間確保・排他制約は占有単位。KPIのスタッフ稼働は占有単位で数える(相乗りの二重計上防止)。

## D-006 定員制の開催時刻
- `schedule_mode = flexible`(営業時間内の刻み) / `fixed`(曜日ごとの固定開始時刻)。ヨガ等のクラスは fixed を推奨。独立した「クラス時間割」モジュールは作らない。

## D-007 強制予約(force)の範囲
- 上書き可能(soft, Owner/Manager + 理由必須 + 監査): 営業時間外、シフト外、休憩/ブロック内、受付期間外(最短予約時間/受付開始)、拠点ブロック、同時受付上限。
- 上書き不可(hard): スタッフの時間重複(他拠点含む)、移動時間不足、リソース容量超過、リソース停止、定員超過、アーカイブ済みスタッフ/サービス/拠点、拠点で提供しないサービス、対応外スタッフ。

## D-008 回数券・利用プランは台帳方式
- 残数はキャッシュ列で、台帳 INSERT トリガのみが更新。直接 UPDATE はトリガで拒否。台帳は追記専用(UPDATE/DELETE 禁止トリガ)。
- 二重消化防止: 冪等キー UNIQUE + 予約行ロック + `bookings.consumption_entry_id`(1予約につき有効な消化は1件)。
- 詳細: PASS_LEDGER.md, PLAN_USAGE_RULES.md。

## D-009 決済は実装しない
- 回数券/利用プランは「外部で購入済みの利用権」を管理する。価格は表示用テキストのみ。支払状態を持たないことで予約/利用権/支払の不整合を作らない。

## D-010 通知は送信箱(outbox)テーブル
- 業務トランザクション内で通知行を INSERT(冪等キー UNIQUE, ON CONFLICT DO NOTHING)。ワーカーが `FOR UPDATE SKIP LOCKED` で取得し送信、指数バックオフで再試行、最大試行後 failed。
- SMTP は厳密な exactly-once を保証できない(送信成功後・記録前にプロセスが落ちた場合)。Message-ID を通知IDから決定的に生成し、受信側での重複排除を可能にする。詳細 NOTIFICATIONS.md。
- 既定 `EMAIL_PROVIDER=log`(実送信しない)。サンプル組織は常に実送信しない。

## D-011 セッションは DB 保存のサーバーセッション
- 理由: 権限変更・スタッフ無効化を即時反映するため。リクエスト毎にセッション→メンバーシップ→ロール/拠点をDBから読む(キャッシュしない)。無効化時はそのメンバーの全セッションを失効。
- Cookie: httpOnly, SameSite=Lax, Secure(HTTPS時), トークンは SHA-256 ハッシュのみ保存。CSRF は同期トークン(`X-CSRF-Token`)+ Origin 検査。

## D-012 パスワードハッシュは Node 標準 scrypt
- ネイティブ依存を避け、どのホスティングでもビルドできるようにする。パラメータ N=2^15, r=8, p=1, 64byte、ソルト16byte。

## D-013 公開予約の顧客照合
- 既存顧客への自動紐付けは「正規化メール一致 かつ 正規化氏名一致」のみ。それ以外は新規顧客を作成し、重複候補として表示(自動統合しない)。予約には入力された連絡先スナップショットを保存し、既存顧客の登録情報は公開フォームから上書きしない。

## D-014 タイムゾーン
- 保存は timestamptz(UTC)。営業時間・シフトテンプレートは拠点ローカル時刻(time)で保存し拠点 timezone で解釈。KPI の「日」は拠点ローカル日付。詳細 TIMEZONE_RULES.md。

## D-015 オフライン
- PWA はアプリシェルと「今日の予定/受付一覧」の閲覧キャッシュのみ。予約確定/変更/キャンセル、来店/完了、回数券消化、権限変更はオンライン必須(オフライン時はボタン無効 + 明示表示)。実施記録の入力は端末内下書き(未同期表示)とし、再接続後にサーバーの最新状態で再検証してから送信。楽観的更新はしない(受付で「完了済み」と誤認させない)。

## D-016 端末テスト
- この開発環境には Chromium のみ(Playwright 1.56 付属)。iPhone/Android/iPad は Chromium の端末エミュレーション(画面サイズ・タッチ・UA)で E2E を実施。実機 Safari/Chrome での確認は販売前の人間確認事項(RELEASE_CHECKLIST.md)。

## D-017 顧客の拠点可視性
- 拠点限定ロール(Manager/Reception)は「自拠点の予約がある」「よく利用する拠点が自拠点」「予約も拠点指定もない」顧客のみ参照可。Staff は自分が担当した(する)予約のある顧客のみ。Owner は全顧客。

## D-018 予約番号・管理トークン
- 予約番号: 紛らわしい文字を除いた8文字(組織内一意)。問い合わせ用で認証には使わない。
- 管理トークン: 32byte 乱数(base64url)。DBには SHA-256 のみ保存。有効期限 = 予約終了 + 30日。照合はレート制限対象。

## D-019 外部カレンダー
- 初版は ICS 出力(予約1件の .ics ダウンロード)のみ。Google/Outlook 双方向同期は Pro 版候補。

## D-020 受付モードは全画面・目安表示
- /app/reception はサイドバーなしの全画面(iPad の受付台想定)。大きなカードで状態をアイコン+文字で表示し、来店/対応開始/完了へ/無断欠席を操作する。
- 回数券/プランは「使えそうなもの(名前・残数・期限)」の目安のみ表示し、消化は完了画面で明示的に行う。目安は予約件数に関係なく固定回数のクエリで取得。
- 他端末の更新は SSE で即時反映し、操作は版番号(expectedVersion)で検出して最新を再表示する。

## D-021 E2E の方針
- 検証対象の操作は画面で行い、前提データ(他拠点の予約・過去の利用など)は同じ認証・CSRF を通る API で準備する。
- E2E 用 DB は毎回作り直し、購入者と同じ CLI(migrate / setup-org / サンプル投入)で準備してからビルド済みサーバーを起動する。
- 複数端末を1本で扱うシナリオ(E2E-1/6)は1プロジェクトで実行し、画面表示の確認は全端末で実行する。

## D-022 利用プランの終了は短縮のみ
- 延長は新しい契約として登録する。終了日をまたぐ期間は打ち切り、終了日後の期間は失効して締める(PLAN_USAGE_RULES.md §8)。

## D-023 無効化した回数券には戻さない
- 返金・誤付与などで無効化した回数券への取消戻しは拒否(PASS_LEDGER.md §5)。失効済みへの戻しは記録できる(再有効化は期限変更で明示的に行う)。

## D-024 待機リストの候補抽出と案内
- 候補は「その時点で空いている枠」を最大10件(希望期間は今日以降・31日以内、希望時間帯と担当の指定に合うもの)。公開予約できる拠点・サービスは公開予約と同じ条件で判定し、お客様が自分で予約できる枠だけを候補にする。
- 再計算のきっかけ: キャンセル・無断欠席・日時変更・復元・予約作成(その日の有効な待機がある場合のみ、SAVEPOINT 内で失敗しても元の操作は成立)、定期ジョブ(15分以上前に計算した待機から順に)。
- 案内は運営者の操作のみ(メール or 連絡済み)。案内前に空きを再判定する。予約は自動で確定せず、確定時点の空きで先着順。
- 同じ顧客が同じ拠点・サービスを待機期間内に予約したら、その待機を「予約済み」にする(候補から予約した場合は待機IDで明示的に紐付け、内容の一致を検査)。

## D-025 ダッシュボードは当日の運営状況
- ロール別に権限のある項目だけを返す(拠点ごとの当日件数・出勤人数・待機、消化確認待ち、期限間近の回数券、送信失敗の通知、Staff は自分の予定と記録未入力)。売上的な指標・稼働率などの経営KPIは KPI 画面(Phase 8)。

## D-026 CSV の出力と取込
- 出力: UTF-8 BOM + CRLF。文字列の先頭が = + - @ タブ CR の場合は ' を前置(数式インジェクション対策。数値型は対象外)。取込時は出力で付けた ' を外す。
- 大きな出力は REPEATABLE READ の読み取り専用トランザクション内でサーバー側カーソルを使い1000行ずつ送る(一貫したスナップショット・メモリ一定)。出力操作は先に監査ログへ記録。
- 取込は新規登録のみ(更新・削除はしない)。プレビューで全行を検証し、エラーが1件でもあれば反映しない。重複の可能性は取り込まない/別人として登録を選び、自動統合はしない。同じ内容(改行コード・BOM を除いた SHA-256)のファイルは二度反映できない(部分一意索引でも保証)。
- 取込対象は顧客・サービス・スタッフ(予約・台帳の取込は整合性の検証が複雑なため初版では対象外。移行はバックアップ/復元で行う)。

## D-027 監査ログの閲覧範囲
- Owner は全件、Manager は担当拠点に紐づく記録のみ(組織全体の設定変更など拠点のない記録は Owner のみ)。Staff・受付は閲覧不可。記録は追記のみ(DB で変更・削除を拒否)。

## D-028 組織単位のバックアップ形式
- 1組織を1ファイル(gzip NDJSON。任意で AES-256-GCM)にする。ヘッダーに形式の版・DB構造の版(最新の移行番号)・アプリの版・作成日時・組織、表ごとに件数と SHA-256、フッターに全体の SHA-256。
- 値は PostgreSQL のテキスト表現(時刻は UTC・マイクロ秒)で持ち、復元時は復元先の列の型へ CAST する(JSON 経由の丸め・時差のずれを避ける)。生成列は含めない。
- ホスティングの DB バックアップ(全組織・時点復旧)を主とし、組織バックアップは誤操作からの復旧・引っ越し・手元保管のために併用する(OPERATIONS.md)。
- セッション・招待・パスワード再設定・レート制限・ジョブ実行記録は含めない(復元で古い招待や認証状態がよみがえらないように)。

## D-029 復元は1トランザクションで、台帳は再生して照合する
- 復元先: new(同じ組織が存在しない環境。空の環境への復元)/ replace(指定した組織を削除して置き換える)。どちらも1トランザクションで、失敗・照合の不一致があれば全体を取り消す(現行データを維持)。dry run は最後に取り消す復元テスト。
- 書き込みはテナント文脈(RLS)で行い、全行の organization_id がヘッダーの組織と一致しないファイルは拒否。ログインユーザーの登録だけシステム文脈で、既存ユーザーは上書きしない(同じID/メールなら紐付け)。
- 回数券/利用プランの残数は 0 で投入し、台帳を元の順序(作成日時順。同じ日時は残数のつながりで並べる)で1件ずつ再生して DB のトリガーに再計算させ、各エントリの balance_after と残数がバックアップと一致することを確認する(必須 #19)。
- 自己参照・循環参照(統合済み顧客、次回予約の元予約、待機⇔予約)は NULL で投入して最後に更新する。その更新で updated_at が変わらないよう、復元中(app.restoring)は set_updated_at を無効にする(移行 0004)。
- 復元後に全表を出力時と同じ形式で読み直し、内容ハッシュを照合する(既存ユーザーへの紐付けを行った表は件数のみ)。
- 復元時点で未送信の通知は skipped にする(古い内容を送らない)。全員のセッションは削除される(再ログイン)。
- 画面からの復元の安全策: 2時間以内の現在データのバックアップ、URL 名の入力、操作者がバックアップ内の有効な Owner であること、別組織のバックアップは追加の確認。

## D-030 セキュリティの網羅テストはルート一覧から作る
- アプリに登録された全 API ルート(`app.routeList`)を列挙し、未ログイン(401)と他組織の ID(成功しない・データを返さない・組織Aが変わらない)を機械的に確認する。ルートを追加すると自動で検査対象になる。
- 一覧の並び順は常に一意になるよう ID を最後の並び替えキーに加える(ページング・復元の照合・画面の安定表示のため)。

## D-031 負荷試験
- 目標規模(組織100・拠点500・スタッフ5,000・顧客50万・予約200万・回数券台帳200万・通知500万)を生成データで作り(`tests/load/generate.ts`、scale で段階的に)、実サーバーを autocannon で測る(`tests/load/run.ts`)。結果は LOAD_TEST_REPORT.md。**販売保証値ではない。**
- 測定で見つかった空き枠計算の遅さ(おまかせの並べ替えで毎回タイムゾーン変換)は、1回の計算内での結果の再利用で解消した(判定内容は同じ)。
